# 发布与打包规则

本文规定 MWJ Docs 可执行文件的版本命名、构建验证、旧包清理和正式发版流程。

## 版本与产物命名

- `version.py` 中的 `__version__` 是打包文件名的唯一版本来源。
- Windows 可执行文件统一命名为 `MWJDocs-v{版本号}.exe`。
- 例如版本号为 `1.5.0` 时，产物必须为 `MWJDocs-v1.5.0.exe`。
- PyInstaller 的 `serve.spec` 和发布脚本共用 `release_config.py` 中的命名规则，禁止在打包命令中手工重命名。
- `pyproject.toml`、`version_info.txt`、README 和 CHANGELOG 中的发布版本必须与 `version.py` 同步。

## Windows 打包命令

在项目根目录运行：

```powershell
uv sync --group dev
uv run python scripts/build_release.py
```

发布脚本会依次执行：

1. 从 `version.py` 读取并校验语义化版本号。
2. 校验 Python 项目版本、Windows 文件版本和原始文件名是否一致。
3. 调用 PyInstaller 构建 `dist/MWJDocs-v{版本号}.exe`。
4. 校验 `--version` 输出以及 Windows `FileVersion`、`ProductVersion`。
5. 将验证通过的 EXE 复制到仓库根目录，作为当前发布产物。
6. 删除仓库根目录和 `dist/` 中的旧 MWJ Docs EXE。
7. 在 `dist/SHA256SUMS.txt` 中生成当前产物的 SHA-256。

## 旧包清理策略

- 只有新 EXE 构建并通过全部版本校验后，才允许清理旧包。
- 清理范围仅限仓库根目录和 `dist/` 目录。
- 只匹配旧的 `MWJDocs.exe` 以及 `MWJDocs-vX.Y.Z.exe`，不使用宽泛的递归删除。
- 当前版本文件不会被清理；同版本重新打包时会安全替换。
- 删除旧包和加入新包应处于同一个发版提交中，仓库只保留当前版本 EXE。
- 已发布到 GitHub/Gitee 的历史 Release 继续保留，便于下载和回退，不属于本地旧包清理范围。

## 正式发版流程

1. 确定新的语义化版本号，例如 `1.5.0`。
2. 同步更新 `version.py`、`pyproject.toml`、`version_info.txt`、README 和 CHANGELOG。
3. 运行全部自动化测试。
4. 运行 `scripts/build_release.py` 构建、验证并清理旧包。
5. 检查仓库中只存在 `MWJDocs-v{当前版本}.exe`。
6. 将版本源码、文档、旧包删除和新包加入放在同一个提交中。
7. 创建与版本一致的 Git 标签，例如 `v1.5.0`，并推送代码和标签。
8. 创建正式 Release，只上传当前版本 EXE 和 `SHA256SUMS.txt`。
9. 核对 Release 资产的 SHA-256 与本地结果一致。

发布过程中任一版本校验、自动化测试或构建步骤失败，都必须终止发版，并保留上一个可用产物。
